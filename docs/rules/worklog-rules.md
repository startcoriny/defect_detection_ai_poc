# Work Log 작성 규칙

## 목적

작업 로그는 단순히 "무엇을 만들었는가"를 기록하는 문서가 아닙니다.

향후 다양한 기술 문서와 프로젝트 기록으로 재사용할 수 있어야 합니다.

예를 들어 다음과 같은 용도로 활용합니다.

* 프로젝트 회고
* 기술 문서 작성
* 기술 의사결정 회고
* 아키텍처 선택 근거 추적
* 다음 세션의 AI 컨텍스트 전달

따라서 작업 로그는 구현 내용보다 문제 해결 과정과 기술 선택 이유를 중심으로 작성합니다.

---

## 제목 형식

Notion "개발 일지" 페이지 하위에 자식 페이지로 기록하며, **하루에 하나의 페이지**만 만듭니다.

같은 날짜에 성격이 다른 작업을 여러 건 진행했다면, 페이지를 나누지 않고 하나의 페이지 안에 작업 단위 섹션으로 모읍니다. 여러 작업이 날짜별로 흩어져 있으면 하루의 작업 흐름을 한눈에 파악하기 어렵기 때문입니다.

페이지 제목은 그날 진행한 작업 내용을 `/`로 이어 붙입니다.

```
YY_MM_DD | 작업1 내용 / 작업2 내용 / 작업3 내용 ...
```

예시.

* `26_07_22 | 개발 환경 구성 / 원본 데이터 확보 및 보존 / 데이터 구조 분석`

내부 작업 번호(`작업1`, `작업6` 등 `docs/context/02-task-list.md`의 태스크 번호)는 제목과 본문 어디에도 넣지 않습니다. 그 번호는 CLAUDE의 설계 단계나 CODEX 지시서(`agent_work/prompt.md`)에서만 쓰이는 내부 식별자이고, 작업 로그 자체는 실제로 한 일을 내용으로 설명해야 하기 때문입니다. 대신 "개발 환경 구성", "데이터 인벤토리 생성"처럼 실제 작업 내용을 그대로 제목/구분 헤딩에 씁니다.

같은 날짜에 이미 페이지가 있는 상태에서 새 작업을 추가로 기록해야 하면, 새 페이지를 만들지 않고 기존 페이지의 제목에 새 작업 내용을 이어 붙이고 본문 끝에 새 섹션을 추가합니다.

---

## 한 페이지 안에서 작업 구분하기

하루에 작업을 여러 건 진행한 경우, 본문은 작업 단위로 구분합니다.

* 각 작업은 `# 작업 내용 제목` (Heading 1)으로 시작합니다.
* 그 아래에 아래 "작성 원칙"의 1~12번 항목을 `##` (Heading 2)로 기록합니다.
* 작업과 작업 사이는 구분선(`---`)으로 나눕니다.

```markdown
# 첫 번째 작업 내용

## 작업 목표
...
## 남은 TODO
...

---

# 두 번째 작업 내용

## 작업 목표
...
## 남은 TODO
...
```

이미 작성되어 있던 항목을 다른 항목과 병합할 때는 문구를 다시 쓰지 않고 원문 그대로 옮깁니다. 특정 항목에 대한 수정 요청(예: 표현 수정, 문구 삭제)이 있었다면 그 항목에만 적용하고, 병합한다는 이유로 다른 항목의 문구까지 확대 적용해 고치지 않습니다. 병합 작업은 구조 재정리(제목 + 구분선)이지 내용 재작성이 아닙니다.

## 작성 원칙

작업 로그에는 반드시 아래 내용을 포함합니다.

### 1. 작업 목표

무엇을 만들려고 했는가.

### 2. 문제 정의

어떤 문제를 해결하려고 했는가.

### 3. 검토한 후보

가능한 해결 방안은 무엇이었는가.

후보마다 아래 내용을 기록합니다.

* 설명
* 장점
* 단점

### 4. 최종 선택

어떤 방식을 선택했는가.

### 5. 선택 이유

왜 해당 방식을 선택했는가.

다음 관점에서 설명합니다.

* 성능
* 확장성
* 유지보수성
* 개발 생산성
* 운영 안정성
* AI 협업 친화성

### 6. 트레이드오프

선택하면서 포기한 것은 무엇인가.

### 7. 구현 내용

실제로 무엇을 변경했는가.

### 8. 변경 파일

변경된 파일 목록.

### 9. 관련 코드 / 프롬프트

의사결정이나 구현의 핵심이 되는 코드, 설정, 또는 CODEX에게 전달한 구현 지시서(`agent_work/prompt.md`) 등이 있다면 원문 그대로 남깁니다.

파일 전체가 아니라 결정과 직접 관련된 부분만 발췌합니다.

### 10. 테스트 결과

어떻게 검증했는가.

CLAUDE가 어떻게 검증했는지뿐 아니라, 사용자가 직접 재현·확인할 수 있는 방법(실행 명령어, 열어볼 파일 경로 등)도 함께 적습니다. `agent_work/review.md`의 "사용자가 직접 확인하는 방법" 섹션이 있다면 그 내용을 그대로 가져옵니다.

### 11. 결과

문제가 어떻게 해결되었는가.

가능하면 수치로 기록합니다.

예시.

* 응답시간 3초 → 0.5초
* 처리시간 30초 → 1초
* API 호출 횟수 80% 감소

### 12. 남은 TODO

추후 작업 목록.

## 중요 규칙

작업 로그는 단순 구현 내역 나열로 끝내지 않습니다.

반드시 아래 질문에 답할 수 있어야 합니다.

* 왜 이 기술을 선택했는가.
* 왜 다른 후보를 선택하지 않았는가.
* 어떤 문제를 해결했는가.
* 선택으로 인해 어떤 이점이 생겼는가.
* 어떤 비용을 감수했는가.

작업 로그만 읽어도 기술 의사결정 과정을 이해할 수 있어야 합니다.
