# Review Agent Rule

Review Agent(CLAUDE)가 코드 리뷰를 수행할 때 따르는 규칙입니다.

## 리뷰 요청

다음 변경사항을 코드 리뷰해주세요.

## 리뷰 기준

1. 요구사항 충족 여부
2. 기존 기능 회귀 가능성
3. 예외 처리
4. 동시성 문제
5. 보안 문제
6. 성능 문제
7. 테스트 누락
8. 과도한 구조 변경
9. 반드시 수정해야 하는 문제와 선택 개선사항 구분

## 산출물 규칙

코드를 직접 수정하지 말고 `agent_work/review.md`에 작성해주세요.

`agent_work/review.md` 마지막에는 항상 "사용자가 직접 확인하는 방법" 섹션을 포함합니다. 사용자가 리뷰 결과를 그대로 믿지 않고 스스로 재현·확인할 수 있도록, 실행할 명령어와 열어볼 파일 경로를 구체적으로 적습니다 (예: `venv/Scripts/python.exe src/xxx.py` 실행, `outputs/xxx/파일명.jpg` 열어서 무엇을 확인하는지, 재현성 확인 방법 등).

## 심각도 분류

### Blocker

배포하면 장애가 발생할 수 있는 문제

### Major

기능 오류 또는 데이터 정합성 문제

### Minor

유지보수성, 네이밍, 구조 개선

### Suggestion

선택적으로 적용할 개선점

## 리뷰 이후 진행 절차

CODEX 구현이 끝나고 CLAUDE가 리뷰를 마쳤다면, 곧바로 커밋·푸시·PR을 진행하거나 진행 여부를 묻지 않습니다.

대신 아래 순서를 따릅니다.

1. 리뷰 결과를 사용자에게 보고합니다. 무엇을 리뷰했는지, 어떤 문제를 발견했는지(또는 문제가 없었는지), 그래서 지금 상태가 어떤지를 설명합니다.
2. 사용자가 결과물을 직접 확인할 때까지 기다립니다.
3. 사용자가 추가로 반영할 내용을 요청하면 그 요청을 다시 CODEX에게 전달해 반영합니다 (필요하면 이 사이클을 반복합니다).
4. 사용자의 최종 확인을 받은 뒤에만 커밋 → 푸시 → PR 생성을 한 번에 진행합니다.
   - "커밋·푸시·PR 진행해줘" 같은 승인은 그 **작업을 진행**해도 된다는 뜻이지, PR 본문이나 Notion Work Log에 **어떤 문구를 쓸지**까지 승인한 것이 아닙니다. `CLAUDE.md`의 PR/Work Log 규칙대로, PR 본문 초안과 Notion Work Log 초안은 각각 실제로 `gh pr create`/Notion 등록을 실행하기 전에 먼저 보여주고 승인받습니다.
   - 커밋과 푸시(원격 브랜치에 올리는 것)는 초안 승인 없이 진행해도 되지만, PR 생성과 Notion 등록은 항상 초안 → 승인 → 실행 순서를 지킵니다.

이유: 리뷰가 끝났다고 바로 "커밋해도 될까요?"를 물으면, 사용자가 아직 결과물을 직접 확인하지 못한 상태에서 매번 같은 질문에 답해야 합니다. 사용자가 직접 확인하고 추가 요청까지 끝낸 뒤 한 번에 커밋·푸시·PR로 이어가는 편이 흐름이 매끄럽습니다. 다만 "진행해줘"라는 승인 한 마디가 PR 본문·Work Log 문구 자체에 대한 승인까지 대신하지는 않습니다 — 실제로 PR #6과 그 Notion 기록을 초안 없이 바로 생성한 적이 있어, 이 구분을 명시해둔다.

## 기계적 포맷 문제는 CLAUDE가 바로 적용

`black`, `ruff --fix`처럼 판단 없이 결정적으로 정해지는 포맷 문제는 리뷰에서 발견해도 CODEX에게 돌려보내지 않고 CLAUDE가 그 자리에서 바로 적용합니다.

CODEX 샌드박스는 한글 사용자 경로 문제로 `venv`를 못 읽어 `black`/`ruff`를 직접 실행하지 못하는 경우가 있어(알려진 제약), 이런 포맷 확인은 어차피 CLAUDE 쪽에서 마무리해야 합니다.

단, 로직·구조를 바꾸는 수정(예: 클래스명 표기, 판정 기준 등 내용이 있는 수정)은 여전히 CODEX에게 전달해서 반영합니다 — 이 예외는 순수 포맷팅에만 해당합니다.

## CODEX에게 전달하는 방식: prompt.md vs 직접 지시

- **새 기능 구현**: 항상 `agent_work/prompt.md`에 구현 지시서를 먼저 작성하고, 사용자 승인 후 `codex exec`로 전달합니다 (`CLAUDE.md` 구현 지시서 작성 규칙 그대로 적용).
- **리뷰에서 나온 scoped fix**: `agent_work/review.md`에 문제와 수정 방향이 이미 구체적으로 적혀 있다면, `prompt.md`를 다시 쓰지 않고 그 내용을 근거로 `codex exec`에 바로 지시문을 넣어 전달해도 됩니다. review.md 자체가 이미 범위가 명확한 지시서 역할을 하기 때문입니다.
- 새 기능과 무관하게 범위가 불명확하거나 review.md에 없는 새로운 요구사항이 섞여 있다면, scoped fix로 보지 않고 `prompt.md`를 다시 작성합니다.

## AI 전용 md 파일 수정은 별도 브랜치·PR을 만들지 않는다

`docs/rules/*.md`, `docs/onboarding/ai-orchestration.md`, `CLAUDE.md`, `AGENTS.md`처럼 AI(CLAUDE/CODEX)가 스스로 어떻게 동작할지를 정하는 문서는, 수정할 때마다 새 브랜치를 파고 PR을 올리지 않습니다. 대신 그 시점에 진행 중이거나 다음으로 시작할 실제 작업 브랜치에 그 변경을 함께 실어서 커밋·PR합니다.

- 진행 중인 작업 브랜치가 있으면 그 브랜치에 바로 커밋합니다.
- 지금 활성 작업 브랜치가 없으면, 워킹 디렉터리에 변경 사항만 남겨두고(커밋하지 않음) 다음 작업 브랜치를 만들 때 그 변경을 함께 커밋합니다.

이 예외는 **AI 전용 프로세스/규칙 문서**에만 해당합니다. `docs/context/`, `docs/reports/data-inventory.md`, `docs/reports/raw_data_structure.md`, `docs/decisions/`, `docs/specs/` 등 프로젝트 자체의 내용(데이터, 설계, 의사결정)을 다루는 문서는 기존 규칙대로 별도 브랜치·PR을 거칩니다.

이유: `docs/rules/review-agent-rule.md`, `worklog-rules.md` 같은 문서는 지난 세션에서 짧은 시간 안에 여러 번 고쳐야 했는데, 매번 별도 브랜치·PR을 만드는 건 실제 프로젝트 진행과 무관한 오버헤드였다.
