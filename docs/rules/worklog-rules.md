# Work Log 작성 규칙

## 목적

작업 로그는 단순히 "무엇을 만들었는가"를 기록하는 문서가 아닙니다.

향후 다양한 기술 문서와 프로젝트 기록으로 재사용할 수 있어야 합니다.

예를 들어 다음과 같은 용도로 활용합니다.

* 프로젝트 회고
* 기술 문서 작성
* 기술 의사결정 회고
* 아키텍처 선택 근거 추적
* 다음 세션의 AI 컨텍스트 전달

따라서 작업 로그는 구현 내용보다 문제 해결 과정과 기술 선택 이유를 중심으로 작성합니다.

---

## 작성 원칙

작업 로그에는 반드시 아래 내용을 포함합니다.

### 1. 작업 목표

무엇을 만들려고 했는가.

### 2. 문제 정의

어떤 문제를 해결하려고 했는가.

### 3. 검토한 후보

가능한 해결 방안은 무엇이었는가.

후보마다 아래 내용을 기록합니다.

* 설명
* 장점
* 단점

### 4. 최종 선택

어떤 방식을 선택했는가.

### 5. 선택 이유

왜 해당 방식을 선택했는가.

다음 관점에서 설명합니다.

* 성능
* 확장성
* 유지보수성
* 개발 생산성
* 운영 안정성
* AI 협업 친화성

### 6. 트레이드오프

선택하면서 포기한 것은 무엇인가.

### 7. 구현 내용

실제로 무엇을 변경했는가.

### 8. 변경 파일

변경된 파일 목록.

### 9. 테스트 결과

어떻게 검증했는가.

### 10. 결과

문제가 어떻게 해결되었는가.

가능하면 수치로 기록합니다.

예시.

* 응답시간 3초 → 0.5초
* 처리시간 30초 → 1초
* API 호출 횟수 80% 감소

### 11. 남은 TODO

추후 작업 목록.

## 중요 규칙

작업 로그는 단순 구현 내역 나열로 끝내지 않습니다.

반드시 아래 질문에 답할 수 있어야 합니다.

* 왜 이 기술을 선택했는가.
* 왜 다른 후보를 선택하지 않았는가.
* 어떤 문제를 해결했는가.
* 선택으로 인해 어떤 이점이 생겼는가.
* 어떤 비용을 감수했는가.

작업 로그만 읽어도 기술 의사결정 과정을 이해할 수 있어야 합니다.
