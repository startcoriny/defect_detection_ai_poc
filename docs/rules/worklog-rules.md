# Work Log 작성 규칙

## 목적

작업 로그는 단순히 "무엇을 만들었는가"를 기록하는 문서가 아닙니다.

향후 다양한 기술 문서와 프로젝트 기록으로 재사용할 수 있어야 합니다.

예를 들어 다음과 같은 용도로 활용합니다.

* 프로젝트 회고
* 기술 문서 작성
* 기술 의사결정 회고
* 아키텍처 선택 근거 추적
* 다음 세션의 AI 컨텍스트 전달

따라서 작업 로그는 구현 내용보다 문제 해결 과정과 기술 선택 이유를 중심으로 작성합니다.

---

## 제목 형식

Notion "개발 일지" 페이지 하위에 자식 페이지로 기록하며, 페이지 제목은 아래 형식을 따릅니다.

```
YY_MM_DD | 작업 내용 요약 또는 키워드
```

예시.

* `26_07_22 | main.py 스켈레톤 추가 & CODEX 실행 방식 변경`

같은 날짜에 성격이 다른 작업을 여러 건 진행했다면, 하나의 페이지에 몰아넣지 않고 작업 단위로 페이지를 분리합니다.

---

## 작성 원칙

작업 로그에는 반드시 아래 내용을 포함합니다.

### 1. 작업 목표

무엇을 만들려고 했는가.

### 2. 문제 정의

어떤 문제를 해결하려고 했는가.

### 3. 검토한 후보

가능한 해결 방안은 무엇이었는가.

후보마다 아래 내용을 기록합니다.

* 설명
* 장점
* 단점

### 4. 최종 선택

어떤 방식을 선택했는가.

### 5. 선택 이유

왜 해당 방식을 선택했는가.

다음 관점에서 설명합니다.

* 성능
* 확장성
* 유지보수성
* 개발 생산성
* 운영 안정성
* AI 협업 친화성

### 6. 트레이드오프

선택하면서 포기한 것은 무엇인가.

### 7. 구현 내용

실제로 무엇을 변경했는가.

### 8. 변경 파일

변경된 파일 목록.

### 9. 관련 코드 / 프롬프트

의사결정이나 구현의 핵심이 되는 코드, 설정, 또는 CODEX에게 전달한 구현 지시서(`agent_work/prompt.md`) 등이 있다면 원문 그대로 남깁니다.

파일 전체가 아니라 결정과 직접 관련된 부분만 발췌합니다.

### 10. 테스트 결과

어떻게 검증했는가.

### 11. 결과

문제가 어떻게 해결되었는가.

가능하면 수치로 기록합니다.

예시.

* 응답시간 3초 → 0.5초
* 처리시간 30초 → 1초
* API 호출 횟수 80% 감소

### 12. 남은 TODO

추후 작업 목록.

## 중요 규칙

작업 로그는 단순 구현 내역 나열로 끝내지 않습니다.

반드시 아래 질문에 답할 수 있어야 합니다.

* 왜 이 기술을 선택했는가.
* 왜 다른 후보를 선택하지 않았는가.
* 어떤 문제를 해결했는가.
* 선택으로 인해 어떤 이점이 생겼는가.
* 어떤 비용을 감수했는가.

작업 로그만 읽어도 기술 의사결정 과정을 이해할 수 있어야 합니다.
